# Storefront UI Plan

For a template that will launch **many shops**, each with its own palette and
products, sharing structure and boilerplate content.

**Status: proposal. Nothing implemented.**

---

## 1. The core idea: one design language, N palettes

The reusability requirement is the most important constraint here, and it points
somewhere specific.

If each shop were a one-off, we would design *around* its colours. Since every
shop shares a codebase and swaps only its palette, the distinctiveness has to
live in the parts that **stay constant**:

> **Colour is the variable. Type, rhythm, density and motion are the constants —
> and they are what make it look designed rather than generated.**

This is also the answer to "make it exclusive". A shop is not memorable because
of its five hex codes; it is memorable because of typographic scale, spatial
confidence and one well-timed motion moment. Those carry across all shops for
free. Get them right once and every shop inherits a point of view.

The failure mode to avoid: shops that differ only in hue and are otherwise
recognisably the same template. The fix is **structural variety tokens** —
density, radius, type pairing — so shop A can be tight-and-technical while shop
B is airy-and-editorial, from the same codebase.

## 2. Style library — recommendation

### Keep shadcn/ui on Radix. Do not migrate.

Researched the 2026 landscape. The finding that settles it:

| Option | Verdict |
|---|---|
| **shadcn/ui + Radix** *(installed)* | 13 components and 6 Radix packages already here. You own the source, so it can be restyled without fighting a vendor theme. **Recommended.** |
| **Base UI** (MUI's new primitives) | Genuinely promising and actively maintained — but **`1.0.0-rc.0`, not stable**. Wrong foundation for a template that will run many production shops. Revisit at 1.x. |
| **Radix directly** | Development slowed after the WorkOS acquisition. shadcn already wraps it. |
| **MUI / Ant / Chakra** | Opinionated visual language we would spend the project overriding. Wrong direction for a distinctive look. |
| **Aceternity / Magic UI / Cult UI** | Motion-heavy showcase components. Tempting, but they are effect libraries, not systems — and heavy JS on PDPs is exactly what fails INP. Borrow ideas, not dependencies. |

**The important point:** shadcn is a *primitive* layer, not an aesthetic. It
"looks generic" only because most projects ship its defaults — Geist/Inter,
`--radius: 0.625rem`, neutral greys. **Our template currently ships all three
defaults.** The distinctiveness comes from the layer above, which is exactly
where we should spend the effort.

### One dependency to add

`motion` (12.42.2, stable) — for a single orchestrated page-load reveal and
considered micro-interactions. Used sparingly and never on the critical render
path, for INP reasons.

## 3. Token architecture — two layers

The whole reusability story lives here.

### Layer A — Brand tokens (per shop)

Generated from a coolors palette. The only thing that changes between shops.

```
--brand-surface     page background
--brand-ink         primary text
--brand-primary     CTAs, links, active states
--brand-accent      badges, highlights, sale
--brand-support     section fills, decorative
+ derived 50–950 ramps and contrast-checked foregrounds for each
```

### Layer B — System tokens (shared, per aesthetic direction)

```
--type-display / --type-body / --type-mono
--scale-ratio          1.200 minor third → 1.333 perfect fourth → 1.500
--density              compact | comfortable | spacious
--radius               0 (sharp) | 0.25rem | 0.75rem | 1.5rem (soft)
--motion-duration / --motion-ease
--elevation            flat | soft-shadow | hard-offset
--border-weight        hairline | 1px | 2px structural
```

Two shops sharing a palette but differing in `--radius`, `--density` and type
pairing read as genuinely different products. That is the mechanism that makes
this template reusable without becoming a monoculture.

### Functional colours — deliberately outside the palette

`success` / `warning` / `error` / `info` are **not** drawn from the brand
palette. If a shop's accent is red, "Sale" and "Error" must not collide. They
are hue-harmonised toward the brand but always remain semantically distinct.

## 4. The 3–5 colour contract

Coolors palettes are five swatches. Roles are assigned by **OKLCH lightness and
chroma**, never by position in the URL:

| Role | Chosen as | Used for |
|---|---|---|
| **Surface** | lightest | Page background |
| **Ink** | darkest | Body text, headings |
| **Primary** | highest chroma in the mid range | Buy buttons, links |
| **Accent** | second highest chroma | Badges, sale, highlights |
| **Support** | remainder | Section fills, dividers, illustration |

With only **3 colours**, Surface and Ink are extended from the nearest swatches
by pushing lightness to the extremes, and Accent falls back to Primary.

**Contrast is enforced, not suggested.** Every foreground/background pairing is
computed; anything failing WCAG AA (4.5:1 text, 3:1 UI) has its lightness
adjusted until it passes, and the admin is told what was changed. A trending
palette that is all mid-lightness must not be able to ship 2.1:1 body text.

**Distribution beats democracy.** Five colours used in equal measure looks like a
swatch card. The rule: one dominant surface, ink for nearly all text, primary
reserved for actions, accent used sparingly enough to still mean something —
roughly 60/25/10/5.

## 5. Typography

Currently **Geist** — a competent Inter-alike, and the single biggest reason
shadcn projects look identical. Replacing it is the highest-impact change
available, and it costs nothing at runtime.

Proposed pairings, one per aesthetic direction (§8). All are variable fonts,
free for commercial use — which matters when the template ships to many shops:

| Direction | Display | Body | Source |
|---|---|---|---|
| Editorial | **Fraunces** | **Satoshi** | Google / Fontshare |
| Technical | **Bricolage Grotesque** | **Switzer** | Google / Fontshare |
| Warm | **Instrument Serif** | **General Sans** | Google / Fontshare |

⚠️ **Licensing must be checked per shop deployment.** Fontshare and Google Fonts
are fine commercially, but a template used across many client shops should never
inherit a font with a per-domain licence.

Type scale from `--scale-ratio`, not hand-picked sizes. Display sizes get
tighter tracking and optical sizing; body copy gets a measure of 60–75
characters.

## 6. Motion

One well-orchestrated moment beats scattered micro-interactions.

- **Page load:** staggered reveal of hero → categories → products (~40ms stagger)
- **Product grid:** image scale on hover, never layout shift
- **Add to cart:** the one deliberately delightful moment — flight to cart, count bump
- **Gallery:** shared-element transition from grid to PDP

**Constraints, because INP is the most-failed Core Web Vital and PDPs are its
worst offenders:** CSS-only where possible, transform/opacity only, no motion
library on the critical path, and everything wrapped in
`prefers-reduced-motion`.

## 7. Page inventory

### Header — needs real work

Currently minimal. It carries category navigation, which Baymard describes as
the store's table of contents.

- Category mega-menu, driven by the `Categories` collection
- Persistent search
- Cart with live count
- Account
- **Announcement bar** — free-shipping threshold and returns window. Attacks the
  39% "unexpected costs" abandonment *before* checkout, which is the cheapest
  place to fix it.
- Mobile: search and categories first; the desktop hero is the wrong shape for
  a thumb.

### Homepage — build a real one

Today `app/(app)/page.tsx` just re-exports the CMS page template. Proposed
blocks, reorderable per shop in Payload:

1. **Hero** — one clear value proposition. First impressions form in seconds.
2. **Category entry points** — visual, direct routes into the catalogue
3. **Featured / new products**
4. **Trust row** — returns window, delivery, secure payment, contact
5. **Social proof** — reviews, ratings, press
6. **Editorial block** — the story; where a shop earns its personality
7. **Newsletter**

### Product page — restructure against Baymard

Only 48% desktop / 38% mobile of sites reach "decent or good" here.

- Gallery with in-scale and model images, zoom, thumbnails
- **Variants as buttons with availability on the button** (57% of sites get this wrong)
- Price, plus unit price where applicable (81% omit it)
- **Delivery estimate + total cost near the buy button** (67% omit; targets the 39%)
- Stock indicator with honest urgency
- **Returns policy linked inline** (44% omit; 60% look for it here)
- Specifications table, key features
- Reviews with photo browsing and merchant responses
- Sticky add-to-cart on mobile
- Related products

### Category / PLP

Grid, filters (price, category, attributes, availability), sort, pagination or
infinite scroll, quick-add.

### Policy & info pages — shared across shops

FAQ, Returns & Refunds, Shipping & Delivery, Terms, Privacy, Contact, About.

These are the reusable-content story: seeded from templates with shop-specific
values (name, address, returns window, delivery times) injected as variables, so
a new shop launches with complete, coherent policy pages instead of lorem ipsum.

## 8. Aesthetic directions — DECIDED

> **Superseded by `2026-07-28-premium-positioning-decision.md`.**
> Direction chosen: **Editorial structure, technical detail** — editorial above
> the fold, dense specification below it. Driven by the €400–1200 price point
> across kitchenware / electronics / outdoor. The three options below are kept
> for the reasoning that led there.

### Original options

The one thing research cannot decide. All three are palette-agnostic, so any
coolors palette works with any of them.

**A. Editorial / Gallery** — product as artwork. Generous whitespace, large
serif display type, asymmetric grids, restrained motion. Suits considered
purchases: home, design, apparel, craft. Ages well.

**B. Technical / Precise** — tight grid, mono accents for specs and SKUs, sharp
corners, dense information, hairline rules. Suits tools, electronics,
components, anything spec-driven where buyers compare numbers.

**C. Warm / Tactile** — soft radii, textured and layered backgrounds, warm
neutrals, generous imagery, friendly serif display. Suits food, wellness,
children's, handmade.

My recommendation: **A**, unless the first shops are spec-heavy. It carries the
widest range of palettes without looking wrong, gives the most room for good
photography, and reads as premium — which supports margin.

## 9. Phasing

| Phase | Contents |
|---|---|
| **1. Design foundation** | Token architecture, type pairing, scale, motion primitives, radius/density. The layer that makes everything else distinctive. |
| **2. Palette engine** | Coolors parsing, OKLCH role assignment, contrast enforcement, admin preview *(spec'd in the design research doc)* |
| **3. Header + navigation** | Mega-menu, search, cart, announcement bar |
| **4. Product page** | Highest conversion impact |
| **5. Homepage** | Composable blocks |
| **6. PLP + filters** | |
| **7. Policy pages** | Templated, variable-injected, shared across shops |

1 and 2 are independent of 3–7. If you want to see something visual quickly,
1 → 4 shows the most.

---

## 10. Decisions needed

1. **Aesthetic direction** — A, B, or C? (§8)
2. **First shop's product category** — a real subject beats a generic demo, and
   it decides whether B is a better default than A.
3. **Structural variety** — should shops be able to differ in density/radius/type,
   or is one fixed look preferred for consistency across the portfolio?
4. **Reviews collection** — build now, or slot only?
5. **Dark mode** — ship, or light-only for launch?
6. **Currency** — still USD-only. Prices appear on every page in this plan.
